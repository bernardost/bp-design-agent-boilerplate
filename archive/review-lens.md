# Review lens

*What "good" means **on this project**. The `/reviewer` skill holds what never bends —
independence, evidence, the findings format, the two-round limit. This file holds the part
that changes from project to project, and the reviewer reads it at the start of every pass.
Written at `/setup`; edit it whenever the standard moves.*

**If this file is still a template, the reviewer says so in its verdict** rather than quietly
reviewing against nothing.

---

## What this project is judged on

*(Numbered, concrete, checkable against an artifact. For design work this is usually:*

1. *Accessibility — contrast, focus order, target sizes, text alternatives.*
2. *Brand and token consistency — no one-off colours, type ramps, or spacing.*
3. *File hygiene in the design tool — named layers, components not copies, no detached
   instances.*
4. *Handoff completeness — states, edge cases, empty and error views, redlines or specs.*
5. *Does the artifact answer the brief, or a more interesting question nobody asked?)*
